For the last few weeks, I have been trying to build rate limiters by myself. When I started, I had one goal — to learn how a request returns 429 from the server.

Even though I still have multiple types of rate limiters left to build, I have learned so much along the way — how round trip calls affect latency, how atomicity in Redis helps prevent race conditions, and a bunch of other things.

## The Architecture

For today's design, my architecture was straightforward:

![Rate limiter architecture diagram](/images/arch-1.png)

Before the request hits the actual server, it hits the rate limiter. The rate limiter pulls the latest data on the number of requests the server got in the last minute, and how many are still left.

If we've hit more requests than we defined, the rate limiter returns 429. Otherwise, it returns 200.

Simple on paper.

## The Problem

But I found something really interesting while building this.

When I used a Redis instance from Upstash, the latency was painfully slow. But when I spun up a Redis instance on my own system, the latency dropped by 96%.

These numbers are real.

## Why This Happened

Here's what I think is going on:

| Factor | Upstash (Remote) | Local Redis |
|--------|-----------------|-------------|
| **Network RTT** | ~20-50ms per call | ~0.1ms (localhost) |
| **TCP handshake** | Full TLS + TCP | Unix socket / loopback |
| **Geographic distance** | Region-dependent | Same machine |
| **Connection pooling** | Limited by provider | Under my control |

Every `INCR`, `EXPIRE`, or `ZADD` in my rate limiter was a round trip. With multiple Redis calls per request, those milliseconds stacked up fast.

Local Redis skips the network entirely. The kernel routes the packet through `lo0` — no NIC, no router, no ISP.

## What I Learned

**Round trips are expensive.** Even 20ms adds up when you're making 3-4 Redis calls per request.

**Atomicity matters.** Using Lua scripts (`EVAL`) bundles multiple operations into one round trip. This is why my sliding window log uses a single Lua script instead of separate `ZREMRANGEBYSCORE` + `ZCARD` + `ZADD` calls.

**Infrastructure is part of the design.** The same code performs completely differently depending on where Redis lives.

**Measure everything.** I wouldn't have noticed the 96% difference if I wasn't logging latency per request.
