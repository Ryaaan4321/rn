## The Problem

Why move beyond fixed window counter? The cons were real.

Suppose we define `max_requests = 60` in a 60-second window. A person hits 60 requests at the 59th second, then 60 more in the next 3 seconds. In a 4-second interval, we processed 120 requests — double the limit.

The fixed window counter has no memory of *when* inside the window those requests arrived. It just resets.

## How It Works

In the sliding window log, instead of having a count to compare the number of requests, we put the **timestamp of each request** in some sort of data structure.

Each time:
1. We remove the entries that are older than the window
2. We count what's left
3. If the remaining amount of requests is less than the ceiling we defined, we let the request pass through
4. Otherwise, we deny and calculate the time it will take for the key to be on duty again

Attaching the Lua script that is used to make it happen.

## The Lua Script

```lua
local key = KEYS[1]
local max_requests = tonumber(ARGV[1])
local window_seconds = tonumber(ARGV[2])
local now = tonumber(ARGV[3])
local member = ARGV[4]

local window_start = now - window_seconds * 1000

redis.call('ZREMRANGEBYSCORE', key, 0, window_start)

local count = redis.call('ZCARD', key)

if count < max_requests then
  redis.call('ZADD', key, now, member)
  redis.call('EXPIRE', key, window_seconds)
  return { 1, max_requests - count - 1, 0 }
end

-- Denied: find oldest entry to compute retry-after (in ms)
local oldest = redis.call('ZRANGE', key, 0, 0, 'WITHSCORES')
local retry_after_ms = window_seconds * 1000
if #oldest >= 2 then
  retry_after_ms = oldest[2] + window_seconds * 1000 - now
end

return { 0, 0, retry_after_ms }
```
